Hi there! We're thrilled that you'd like to contribute to this project. Your help
is essential for keeping it great.

We accept pull requests for bug fixes and features where we've discussed the
approach in an issue and given the go-ahead for a community member to work on
it. We'd also love to hear about ideas for new features as issues.

We track issues on our project board [here](https://github.com/orgs/Parallels/projects/6/views/1).

Please do:

* Check existing issues to verify that the [bug][bug issues] or
  [feature request][feature request issues] has not already been submitted.
* Open an issue if things aren't working as expected.
* Open an issue to propose a significant change.
* Open a pull request to fix a bug.
* Open a pull request to fix documentation about a command.

Please avoid:

* Opening pull requests for issues marked `needs-design`, `needs-investigation`,
  or `blocked`.

Contributions to this project are released to the public under the
[project's open source license](LICENSE).

Please note that this project is released with a
[Contributor Code of Conduct][code-of-conduct]. By participating in this project
you agree to abide by its terms.

## Branch model

This repository uses two long-lived branches:

| Branch | Purpose |
|--------|---------|
| `main` | Always releasable. Bug fixes and small work merge straight here. Every push is auto-synced into `dev`. |
| `dev`  | Integration branch for big features that need extended staging testing. Merged into `main` once validated. |

Rules:

* Bug fixes, documentation and small changes → PR against **`main`**.
* Big features that need a lot of testing → PR against **`dev`**.
* `dev` is kept current by an automatic `main → dev` merge
  (`sync-main-to-dev.yml`). On conflict it fails loudly — resolve with
  `git checkout dev && git merge main`, then re-run the workflow.
* Never rebase or force-push `dev`.
* `CHANGELOG.md` and `VERSION` are only ever touched on `main`, by release
  automation. **`dev` never edits them** — captured at integration time
  instead (see below).

### Testing a `dev` feature on staging

* **Dev preview** (fast lane): run the `Dev Preview Deploy` workflow from the
  `dev` ref — it builds `ghcr.io/parallels/prl-devops-service:dev-<sha>` and
  deploys it to staging. No GitHub release, no version bump.
* **Full channel cycle**: dispatch `Release Beta` or `Release Canary` from the
  `dev` ref; they build that ref and deploy to staging.

### Landing a `dev` feature on `main`

1. Open the `dev → main` pull request (title it "Integrate <feature>").
2. `update-dev-integration-pr.yml` automatically fills the PR's
   `## Changelog` section with every change merged into `dev` since the last
   integration and labels the PR `dev-integration`. Do not hand-edit that
   section — it is regenerated on every push to the PR branch.
3. Merge it. Bug fixes that went straight to `main` in the meantime are
   unaffected — the next release picks up both streams.

## Changelog section (required in every PR body)

Release notes and `CHANGELOG.md` are generated from the `## Changelog` section
of merged PR bodies. List every user-visible change as one bullet, using these
prefixes:

```
- feat: ...
- fix: ...
- perf: ...
- refactor: ...
- docs: ...
- test: ...
- chore: ...
```

Dependabot PRs are collected automatically from their titles — no action
needed. On `dev → main` integration PRs the section is fully generated by
automation and must be left alone.

## Prerequisites for running and testing code

These are one time installations required to be able to test your changes locally
as part of the pull request (PR) submission process.

1. Install [Go](https://golang.org/dl/) for Mac
2. Install [VS Code](https://code.visualstudio.com/download) for Mac
3. Install [Parallels Desktop](https://www.parallels.com/uk/products/desktop/pro/)
   for Mac
4. Install [Hashicorp Packer](https://www.packer.io/downloads) for Mac
5. Install [Vagrant](https://www.vagrantup.com/downloads.html) for Mac
6. Install the dependencies. From the repository root run:

```bash
cd src
go mod download
go mod tidy
```

## Dev loop & Testing changes

The API is written in go to start it in debug mode you can go to Visual Studio
Code `Run and Debug` and select the Parallels Desktop Api. This will start the
service in debug mode and you can then use the swagger documentation to test
the endpoints.

**Attention** There are some environment variables that might need to be set
so you will need to create a .env file in the root of the repository and add the
following variables:

```bash
ROOT_PASSWORD=<root_password>
```

### Build

Build changes (one time):

```bash
go build ./src
```

### Running tests

```bash
go test ./src/...
```

## Submitting a pull request

1. [Fork][fork] and clone the repository
2. Configure and install the dependencies (in the repository src folder):
   `go mod download`
3. Branch from the right base — bug fixes/small work from `main`, big features
   that need staging testing from `dev`:
   `git checkout -b my-branch-name origin/main` (or `origin/dev`)
4. Make your change, add tests, and make sure the build and tests still pass
   (`go build ./...` and `go test ./...` from `src/`)
5. Fill the **`## Changelog`** section of the PR body — release automation
   reads it (see [Changelog section](#changelog-section-required-in-every-pr-body))
6. Open the pull request against `main` or `dev` accordingly and
   [submit it][pr]

Here are a few things you can do that will increase the likelihood of your pull
request being accepted:

* Format your code with [prettier](https://prettier.io/).
* Write tests.
* Keep your change as focused as possible. If there are multiple changes you
  would like to make that are not dependent upon each other, consider submitting
  them as separate pull requests.
* Write a [good commit message](http://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html).

## How releases work

1. A maintainer dispatches the **Create release PR** workflow on `main`. It
   bumps `VERSION`, regenerates docs/blog/helm artifacts and writes the next
   `CHANGELOG.md` section from the `## Changelog` of every PR merged since the
   last release — bug fixes from `main` and everything integrated from `dev`.
   It opens a PR labelled `release-request`.
2. Merge the release PR. A **draft** GitHub Release is created (its notes are
   taken verbatim from the changelog entry).
3. Publish the draft when ready — `release.yml` then builds the binaries and
   containers and runs the production deployment.
